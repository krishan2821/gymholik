1. Architecture Overview & System Topology

Gymholik implements a modern, decoupled client-server architecture. The mobile client is a cross-platform React Native / Expo application communicating over HTTPS with a high-performance Spring Boot 3 RESTful API backed by a scalable MongoDB document database.

3. Multi-Tenancy Architecture & Data Isolation

Gymholik utilizes a Shared Database, Shared Schema multi-tenancy model partitioned via a required gymId foreign key on every tenant-scoped document.

3.1 The TenantContext Pipeline

  1. Every authenticated request carries a Bearer JWT containing gymId, userId, and role in its claims.
  2. JwtFilter parses the token, authenticates the user principal, and extracts gymId.
  3. TenantFilter establishes a ThreadLocal context via TenantContext.setGymId(gymId).
  4. Service layers query repositories with criteria pre-filtered by TenantContext.getGymId().
  5. In finally block of filter, TenantContext.clear() prevents thread reuse contamination.
public class TenantContext { private static final ThreadLocal<String> CURRENT_GYM = new ThreadLocal<>(); public static void setGymId(String gymId) { CURRENT_GYM.set(gymId); } public static String getGymId() { return CURRENT_GYM.get(); } public static void clear() { CURRENT_GYM.remove(); } }

4. Security Architecture & Threat Modeling

4.1 Authentication & Token Lifecycle

  • Access Token: Short-lived HMAC-SHA256 JWT (expires in 30 minutes). Contains identity and role payload.
  • Refresh Token: Cryptographically secure UUID stored in MongoDB (expires in 30 days). Evaluates token rotation upon exchange.
  • Brute-Force Rate Limiting: Memory-backed sliding window rate limiter (LoginRateLimiter) blocks IP addresses after 5 failed login attempts per minute.

4.2 Privacy & Data Masking

To adhere to privacy standards and prevent competitor staff poaching:

  • Member mobile numbers are masked for staff unless explicitly permitted by gym settings: +91 98****1211.
  • Gym secret codes are visible exclusively to verified gym owners.
